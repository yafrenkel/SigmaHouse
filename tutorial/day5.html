Day 5 — Houses Talking to Each Other

Goal: Make your house send a text message to a friend's house, through the hub. Their board prints it in the Thonny console (and flashes it on the LCD). No new hardware — you already have everything. By the end, one board can message any other board in the room.

🔑 The big idea: a house never talks directly to another house — it can't even reach it. Every message goes through the hub: you drop a note in a friend's mailbox on the server, and their board picks it up on its next keepalive. Same "the board always speaks first, the hub answers" rule from Day 3.

Part 1 — The mailbox API (10 min)

Every house now has a mailbox on the hub. It's a tiny REST resource — remember Day 1's collection vs. item? The mailbox is a collection that lives under your house:

/api/houses/<uid>            <- one house  (the item)
/api/houses/<uid>/messages   <- that house's mailbox  (a collection)

Two verbs act on it, plus one new flag on the keepalive you already know:

Verb + URLMeansResponse
POST /api/houses/<uid>/messagesleave a message for that house201 {"ok": true}
GET /api/houses/<uid>/messagesread and empty your own mailbox200 {"messages": [ … ]}
PUT /api/houses/<uid>/keepalivethe heartbeat — now also reports mail{"alarm":…, "state_update":…, "message": true|false}

The message body is just {"from": "<who>", "text": "<≤32 chars>"}. A message to a house that doesn't exist is a 404; empty or too-long text is a 400.

💡 Reading empties the mailbox — exactly like GET /state clears the state_update flag from Day 3. Once your board reads its mail, the next keepalive says message: false again. A message is delivered once.

Part 2 — Send your first message (20 min)

Pair up with a neighbor. You'll need their house ID (the full unique_id). Two easy places to find it:

  • It prints in their Thonny shell at boot: My house ID: A1B2C3D4E5F6 …
  • It's the House ID column on the dashboard.

Warm-up — send from your laptop

🛠 Try this in PyCharm's terminal (swap in your friend's ID and the real hub URL):

curl -X POST http://192.168.1.42:8080/api/houses/A1B2C3D4E5F6/messages \
  -H "Content-Type: application/json" \
  -d '{"from":"me","text":"hello neighbor!"}'

Within ~1 second, your friend's Thonny shell prints:

>>> MESSAGE from me : hello neighbor!

…and their LCD flashes Msg me / hello neighbor! with a short beep. 🎉

🧪 No terminal? Send from the dashboard or the browser console instead.

On the dashboard, click the Send button in your friend's row — a popup asks for the text. Or paste this in the browser console (F12) while on the dashboard:

fetch("/api/houses/A1B2C3D4E5F6/messages", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ from: "me", text: "hello neighbor!" })
}).then(r => r.json()).then(console.log)

The real deal — send from YOUR house

That last one came from a laptop. Now let's send from the board itself — house to house. Here's the trick: Thonny's Shell is a Python prompt running on your ESP32. Anything you type there runs on your board, so when you call send_message, your house makes the request.

🛠 Try this:

  1. Your firmware is running. Press Ctrl-C in the Shell to stop the loop — you get a >>> prompt.
  2. Your house is still on WiFi and still knows who it is. Send: 
    >>> import app_sync
>>> app_sync.hub.send_message("A1B2C3D4E5F6", "hi from my house!")
{'ok': True}
  3. Press Ctrl-D to reboot the board and restart the firmware (keepalives resume).

app_sync.hub is your house's connection to the hub — we left it reachable from the REPL on purpose so you can do this. send_message puts from = your own ID automatically, so your friend sees exactly which house wrote.

▶ Want to see the raw request? Build the JSON yourself.

This is what send_message does under the hood — the same urequests you used on Day 3:

>>> import urequests, config
>>> r = urequests.post(
...     config.HUB_URL + "/api/houses/A1B2C3D4E5F6/messages",
...     json={"from": "my house", "text": "hi!"},
...     headers={"Content-Type": "application/json"})
>>> r.status_code
201
>>> r.close()          # ALWAYS close it (Day 3 rule!)

👀 Watch your own row while you're paused. While you sit at the >>> prompt, your board isn't sending keepalives — so after 60 s the dashboard flips your house to Lost (red). Ctrl-D brings it back to Active. That's the Day-1 watchdog doing its job, live. Send fast, then Ctrl-D!

✅ Milestone 5.1: A message you sent from your board's REPL shows up in a friend's Thonny shell.

Part 3 — How it works (15 min)

Follow one message from your keyboard to your friend's screen. Every hop lives in a file you can open:

#What happensWhere (file · function)
1You POST a message → the hub drops it in the target's mailbox list.iot_hub/app.py · leave_message() → houses.py · send_message()
2Their board's next keepalive answer includes message: true (mailbox not empty).iot_hub/houses.py · keepalive()
3The board sees the flag and does a GET …/messages.smart_house/app_sync.py · the keepalive block → hub_client.py · get_messages()
4The hub returns the list and empties the mailbox — so the flag is false next time.iot_hub/houses.py · get_messages() (it pops)
5The board prints each message to the console (and shows the newest on the LCD).smart_house/app_sync.py · _show_messages()

It's the exact same shape as the alarm and the LED toggle from Day 3: the hub can't call the board, so it raises a flag on the keepalive, and the board pulls the details when it's ready. Learn this one pattern and you understand the whole system.

🛠 Try this: open smart_house/app_sync.py and find the keepalive block. The message handling is just two lines, right next to the state_update two lines it copies:

if resp.get("message"):
    _show_messages(hub, lcd, buzzer)
🤔 Why does the mailbox empty when I read it, instead of staying?

So a message is delivered once. If reading didn't clear it, the flag would stay true forever and your board would re-print the same message every single second. "Read = drain" (a queue) is the simplest way to guarantee each message is shown exactly one time — the same reason GET /state clears state_update.

Part 4 — Send from the house itself, with a button (30 min)

So far you sent messages from a laptop (curl, the dashboard) or from the REPL. Now let's send with a button on the board — no laptop at all.

Your house already uses the buttons like this: button A scrolls a little menu (led → fan → buzzer) and button B acts on the selected one. We just add a message target to the end of that menu. Scroll A onto it, press B, and your house sends. Who receives depends on one setting in config.py:

SEND_MODEButton A scrolls to…Press B →
"fixed"… buzzer · msgsend to the one friend in MESSAGE_TO
"broadcast"… buzzer · msgsend to every other house at once
"pick"… buzzer · HOUSE1 · HOUSE2 · …send to the house you scrolled to

🛠 Try it — "fixed" mode

  1. In config.py, set SEND_MODE = "fixed" and paste a friend's ID into MESSAGE_TO.
  2. Run the firmware. Press A until the LCD shows Select: msg.
  3. Press B. The shell prints Button B -> sent to <id> : {'ok': True}, and your friend's house prints your message.

✅ Milestone 5.2: A button press on your board messages a friend.

✅ Milestone 5.3: You can scroll to any house and message it from the board.

💡 The sneaky edge case: houses come and go, so the menu is rebuilt every few seconds. If a house you'd scrolled to goes Lost, the list shrinks — the line if menu_index >= len(menu): menu_index = 0 keeps the pointer from falling off the end. Delete it and a disappearing house crashes your loop with an IndexError.

Bonus — Talk in Morse code 📻 (no coding required)

Here's the neat part: the message system already carries any text, so you can send secret Morse-code messages without changing a single line of code. Morse is just the message content — dots and dashes typed into the text.

🛠 Try this: spell a short word in dots (.) and dashes (-) using the chart below, then send it any way you already know — all of these take plain text, so none need code:

  • Dashboard — click Send, type ... --- ... into the popup.
  • REPL (after Ctrl-C) — app_sync.hub.send_message("FRIENDS_ID", "... --- ...")
  • Button B — put your Morse in config.MESSAGE_TEXT (that's a setting, not code) and press B.

Your friend reads the dots and dashes in their Thonny console (it shows the whole message — the LCD only fits the first 16 characters) and decodes them back to letters. The buzzer's little beep just says "mail's here!" 🔔

Two rules that make it readable

  • One space between letters: H I → .... ..
  • A slash between words: HI DAD → .... .. / -.. .- -..

💡 Keep it short — a message is capped at 32 characters, so aim for one short word or a callsign (about 5 letters of Morse).

Start with the famous one: SOS = ... --- ... — three dots, three dashes, three dots.

What you learned today

  • A mailbox is just a REST collection under a house: /api/houses/<uid>/messages, POST to fill, GET to drain.
  • The flag-then-pull pattern again: keepalive says message: true, the board fetches — the hub can never call the board first.
  • Reading empties the mailbox, so each message arrives exactly once.
  • The Thonny Shell runs on your board — app_sync.hub.send_message(...) after Ctrl-C is your house talking, and Ctrl-D resumes.
  • Pausing the loop makes your house go Lost — the watchdog, live.
  • Sending from the board: button A scrolls a menu, button B sends; SEND_MODE picks fixed / broadcast / pick.
